Product work with an AI coding agent

A working building-safety tool built end to end by directing an AI coding agent, run like a real engineering workstream rather than an ad-hoc prompt session.

Role: Product owner and sole developer, directing the AI coding agent, Claude Code. Timeframe: 2 days Tools: HTML, CSS, TypeScript, no framework, localStorage, Claude Code, Firebase, GitHub
View the live tool! View the code on GitHub

Overview

I wanted to test a specific idea: that a product manager's job on an AI-native team is not to hand a tool a prompt and accept what comes back, but to direct it with the same rigour you would bring to a real engineering workstream.
So I built a working fire-risk-assessment remedial-action tracker, the kind of tool the UK building-safety industry runs on, where each finding becomes an action with an owner, a priority, and a target date, moving through the lifecycle that forms the auditable record compliance depends on.

The point was not the final code, it was the delivery to a working example.

This is the hands-on companion to my scoping and ticketing case study, where I took a similar building-safety product from an approved concept to a build-ready backlog for a team, rather than building it myself.

Approach and build

What I built

A deliberately small but functional slice: a browser-based tracker that lists remedial actions, each with a building reference, description, priority, owner, target date, and status. You can add an action with validation, so required fields are enforced and a target date cannot be in the past, update a status straight from the list, and filter by status, priority, building, or overdue. Everything persists in the browser with no backend and no accounts.

It is a learning and portfolio piece, not a commercial product, and it was scoped that way on purpose: just enough working software to prove the delivery approach.

How I ran it

Rather than a loose chat with an AI, I ran it like an engineering workstream: versioned checkpoints, a written working agreement, conventional commits, and a dated decision log that tagged every decision by type, whether I directed the agent, overrode its output, or corrected its process.
My user stories were written to a reusable structure, so a fresh agent session could pick up any one of them and build it with no re-explanation.

The documentation lived alongside the build (all visible on Github!), a product brief with the original scope and success criteria, a running project summary of what shipped and what was deliberately left out, and the decision log itself.
