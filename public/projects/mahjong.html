Mahjong Hand Calculator

A real-time decision support tool for the complicated game of Mahjong.

Role: Product owner and sole developer Timeframe: 21 build sessions with 2 feedback rounds over 3 months Tools: React 18, TypeScript, Vite, Firebase Hosting, Google Analytics, Claude AI
View the live tool! View the code on GitHub

Overview

Mahjong scores a hand from dozens of interlocking combinations, and holding that whole picture in your head during live play is exhausting, especially for newcomers.

So I created something that didn't exist before!

This tool takes your current tiles and, in real time, works out every scoring hand they could form, how many tile exchanges you are from each useful shape, and which tile to discard.

I built it to solve my own problem at the table, and I use it during real games.

The Problem

Mahjong rules are well documented, but they are dense and deeply interdependent:
31 distinct scoring patterns, three different winning hand shapes, and scoring that changes depending on how the same tiles are read.

For newcomers, holding all of that in your head, during live play, is the real barrier.

So unlike my other projects, the hard part here was never research; it was delivery. The rules were a known quantity.
The challenge was turning a well-defined but very intricate rule set into calculations that stay correct in every edge case and still fast enough to feel instant as the tiles change.

Approach and decisions

A real engine, not a lookup table

Simply put, there is no clean table that one can pull the results from. Instead, the core logic is a recursive backtracking validator that checks a hand against all 31 yaku, paired with a shanten calculator that works across all three hand shapes and reports how far the hand is from completion.
The difficulty was correctness under interdependency: whether a hand qualifies for Pinfu depends on how it is decomposed and which wait shape results, and Fu and Yakuman carry their own supersession rules.
Making a simple lookup table would have been easier to do but also broken on the many edge cases, so I built a proper logic engine instead.

Deciding what to include and show

The later decisions were less about what to build and more about where to stop.
Mahjong has many moving parts: the tiles in hand, the mandatory shapes and yaku, player positions, han scoring, and more. I drew the line at the closed hand.
The tool fully covers every closed-hand possibility, which is what lets it stay correct and fast, and I deliberately shelved open-hand simulation as an explicit scope cut rather than letting it creep in.
The trade-off is simple: the tool fully covers all personal, close-handed possibilities, so it can stay correct. The alternative was effectively a full table simulation, like the paid games offer, which would have multiplied the scope.

Underneath the features, I ran it as a delivery rather than a random hobby.
Each of the 21 sessions scoped, researched, and documented a feature in a living project brief before any code was written, so a session could always resume with full context. Partway when the code became too large, I refactored the calculation logic into a single hook and moved shared helpers into their own module to resolve circular dependencies, which kept the codebase workable as the feature set grew.
That is end-to-end ownership I had: not only deciding what to build, but keeping it easy to work with.

Outcome and impact

31 yaku checks
51 calculations per hand
~10+ trillion possible hands
1 delivered product!

The tool is deployed and live, feature-complete across the scope I set, and in real use, by me and friends, during actual games.
That is the most honest signal I can give: I can personally vouch for it because it solves the problem it was built for.
It also gave me a working reference for the arc of owning something small but real, keeping it in scope, from the many problems to being shipped and maintained.

Reflection

There were two main takeaways while working on this:
The clearest lesson was that a well-defined problem is not the same as an easy one: even as all the rules being defined at the beginning, it was no wonder I found no other calculators that do what this one does. The scope of actually calculating distances and providing recommendations is much higher than the end-result checking that other calculators do.

The other lesson was obvious: every project needs a second pair of eyes.
The multiple feedback rounds from friends were very helpful. They raised issues I did not think of, edge cases that slipped through, or UX problems that made it way more intuitive to use.
